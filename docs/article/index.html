Building a React-like JSX runtime with generator functions

Six months of evenings, countless rewrites, a shift from vibe coding to writing most of it by hand, one shelved idea, and a lot learned along the way.

For the last six months I've been building yract, a client-side JSX runtime with synchronous rendering, in my free time. It follows React's API closely, but makes some different design decisions and adds a few things I've always wished React could do. It's an experiment, not a library you should use yet; more on that at the end.

I had two motivations. The first was simply that I wanted to understand how a runtime like React works under the hood: to work through the same problems myself and see whether I'd arrive at React's solution or a different one. The second was practical. Over the years I've worked around the same issues in client-side React in project after project, and I felt some of them could, and should, be solved in the library itself.

What yract does differently

1. Components and hooks are generator functions

A component is a generator function: hooks are called with yield*, and the JSX is the return value. Because hooks are generators too, a hook can do more than hand back a value. It can end the component's render and show UI itself, so a custom hook can own its loading and error states and the component only deals with the loaded data. In theory, generators would also let a render resume later instead of re-running the whole component function.

Ending the render early is just return yield child. Yielding any child, whether an element, a string or null, ends the component's render on the spot and renders that child instead. It works from deep inside a custom hook like useUser too, because the hook's yield reaches the renderer through the component's yield*. The component never gets past that line, so it only ever deals with the loaded user. The one catch: a generator that returns early this way needs a return-type annotation, like ComponentGenerator<User> here.

2. Hooks can be skipped by returning early

Hook order matters just like in React: hooks are matched by the order they're called, so you can't call one conditionally in the middle of a component. What's different is what happens when a render ends early. In React, a render that calls fewer hooks than the previous one throws "Rendered fewer hooks than expected". In yract, a component can return early, with a plain return or return yield, before it reaches its remaining hooks.

Skipped hooks are treated as unmounted: their effects clean up and their state is dropped. The next time the component reaches them, they start fresh.

3. Better defaults for hooks

Most React codebases I've worked on end up with the same handful of helper hooks: a callback that never changes identity, an effect that can be cancelled, a context hook with a selector. Teams might write their own versions, each slightly different (with different bugs), and new developers don't always know they exist, so they reach for the built-in hook and get the old pitfalls back. Most of those pitfalls come from dependency lists: a missing dependency leaves stale values, and an extra one makes a callback change identity or an effect run too often. So I tried to make the built-in hooks handle the common case safely, so that the easy way is also the right way.

useMemo: dependencies are passed to the callback

yract's useMemo passes the dependency list to your function as its arguments, and recomputes only when one of them changes. That means the function can live outside the component.

Why? The classic useMemo bug is a value the function uses but the dependency list doesn't include, so the result silently goes stale. When the function only receives what's in the list, it can't read anything else by accident. As a bonus, the component body gets shorter.

useEffect: every effect gets an AbortSignal

yract's useEffect passes each run an AbortSignal. The signal aborts before the effect runs again and when the component unmounts, and the effect itself can be async.

Why? Effects often do something async, and the rest of the work should be skipped if the dependencies change or the component unmounts before the async part is done. In React that means a hand-rolled aborted flag and a cleanup function in every such effect. An AbortSignal does the same job and plugs straight into fetch and most async APIs.

useCallback: no dependency list

yract's useCallback always returns the same function reference, but when it's called, it runs the latest version of your function, so it always sees the current variables (props, state, etc.).

Why no dependency list? In React, the dependency list does two jobs at once, and they pull against each other. List too few dependencies and the callback reads stale values. List all of them and the callback gets a new identity whenever they change, which rerenders memoized children and re-runs effects that depend on it. Most of the time, what you actually want is a function that never changes identity but always does the current thing, so in yract that's the default.

useContext: choose when a context change rerenders you

yract's useContext takes an optional selector that picks the parts of the context the component depends on. The component rerenders only when one of those parts changes.

Why? In React, every consumer of a context rerenders whenever the provided value changes, even if the part it reads stayed the same. The usual workarounds are splitting the context into many small ones, or moving the state out of React into an external store with selectors. With a selector built in, one context can serve a large tree: in the playground's 6000-row table, changing the highlighted city rerenders only the rows whose highlight actually changed.

4. Its own scheduler and reconciler

Under the hood, yract doesn't reuse anything from React. The scheduling and reconciliation are written from scratch:

  1. Scheduling. The biggest difference from React is the order in which components render:
    • React walks the tree depth-first: a component's child, then the child's child, before moving on to siblings.
    • yract puts components into a queue grouped by depth and renders level by level: every scheduled component at one depth before anything deeper. A parent's render adds its children to the queue instead of rendering them on the spot.
  2. Reconciliation. Each render records its DOM work as a list of actions instead of touching the DOM directly. Keyed children are matched so that a reorder moves as few DOM nodes as possible, and a newly mounted subtree is built off-screen and inserted with a single DOM operation.

The hardest problem: a <Defer> component

The most ambitious thing I tried was combining what <Suspense> and useDeferredValue / startTransition do into a single <Defer> wrapper component. Narrowing the scope

I worked on this for months, through countless rewrites, learning more with each one. Then life handed me other responsibilities 👶🍼. So I narrowed the scope sharply, shelved the <Defer> idea, and kept just the simpler, synchronous JSX runtime described above: smaller in scope, but with the ideas I cared about most.

What I learned working with Claude Code

This project also taught me a lot about working with an AI coding agent. I used Claude Code throughout, but I didn't hand it the architecture. The design decisions were mine: generator components, the hook defaults, and how scheduling and reconciliation work.

Where Claude Code helped most was planning. Before any hands-on work, I talked each change through with it: organizing my thoughts, weighing the options and finding the edge cases up front. It was also great at finding the very human bugs I had written myself. In the end I wrote about 98% of the library code myself, and the final code is something I understand line by line. The tests were the exception: Claude Code wrote most of them, so I didn't have to write them by hand.

The biggest lesson was that the agent is only as good as the direction you give it. Clear intent and small, well-defined steps worked much better than asking for big changes in one go.

That lesson applies to me as well. While writing this article, I realised I would probably have got further with my original goals if I had first implemented just <Suspense> on its own. I guess I was having too much fun building to stop and think 😅

Not ready to use, and that's fine

yract is a learning project, not a production library. There are still big gaps: no server rendering or hydration, no Suspense or lazy loading, no error boundaries, no portals, no devtools, and no capture-phase event props. The API will keep changing as I learn more. Please don't build anything important on it, but do read the code if you're curious how a JSX runtime works underneath.

Working on this project taught me a lot about building systems and about working with AI. Many of React's choices that once felt arbitrary make a lot more sense after you've tried to build something similar yourself.

The code is on GitHub: github.com/jEnbuska/yract. I'd love to hear which of these ideas you'd want in React, and which ones you think are a bad idea.
